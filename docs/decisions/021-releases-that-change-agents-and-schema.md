# 021: Releases: agents re-synced from the build, migrations that only add

**Date:** 2026-11-11 · **Status:** accepted 2026-11-11 (built in the same commit) · **BUILD_PLAN:** Step 8, deployment

## The question

Two things a release did badly, found getting ready for one that carries about 30 commits and 15 migrations at once.

1. **A prompt change never reached the agents already at Retell.** The sync job sent a profile once per version and skipped a synced one. So the prompt changes made since the demo agent was created on 2026-11-10 (the gas reminder, never saying an amount of money, the read-backs) wouldn't have reached the demo line with the next release. They'd only have gone live when the business next saved a change to its profile. The same goes for the API's address after the domain move, which RUNBOOK section 16 handled with a manual `save-demo-profile` task.
2. **Nothing stopped a migration from breaking the build still running.** A release runs the migrations, then moves the apps to the new image. The old API keeps answering calls until the new one is ready: for a few minutes, or for as long as the new one fails its check. A migration that drops, renames or tightens something the old code uses would break calls in that window. Every migration so far only adds, but only by habit.

## Options for 1 (agents)

| Option                                                                                                                                                                         | For                                                                                                                                                                                                | Against                                                                                                                                 |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **The worker re-checks every agent after start-up; a sync re-sends a synced version when what it would send has changed (a fingerprint of the exact Retell request)** (chosen) | Automatic on every release and every `apply`, so the domain move's re-sync comes free; sends only to agents that differ; covers the adapter (model, voice, webhook addresses), not just the prompt | One sync job per business at each worker start, most of them a database read and nothing else; needs care around the old worker (below) |
| A version number in the code, bumped by hand when the prompt changes                                                                                                           | Simple                                                                                                                                                                                             | Forgotten once and the agents are stale with nothing to show it; misses the address and the adapter                                     |
| A Deploy task that re-syncs everyone, run by hand after a release                                                                                                              | Nothing automatic to get wrong                                                                                                                                                                     | One more step after every release, and a forgotten one is silent                                                                        |
| Re-sync every agent on every start, changed or not                                                                                                                             | No fingerprint to keep                                                                                                                                                                             | A Retell update per business per restart, for nothing; at 1,000 businesses, 4,000 API calls each time                                   |

**The old worker.** A release starts the new worker before stopping the old one, and both work the same queue. If the old worker took a re-check job, it would compare against its own build, find nothing changed, and finish the job, leaving that agent on the old prompt. So the new worker waits two minutes before queuing the re-checks (`RESYNC_CHECK_DELAY_MS`). Two minutes is our estimate of the overlap: Azure doesn't document how long the old revision of an app without ingress keeps running.

**Confidence:** high that it re-syncs what changed (tests for the fingerprint, the re-send to the same agent, the older-version guard and the list of businesses); moderate on the two-minute wait.

**Strongest case against:** a re-sync changes a live agent with nobody watching. A prompt change that's wrong goes to every business at the next release, not just to the next business that saves its profile. But the change was already meant for everyone, and the evals check it before a commit. Sending it everywhere is the point; leaving it stale wasn't a safety net.

## Options for 2 (migrations)

| Option                                                                                                                                                                                                                               | For                                                                                                                       | Against                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **A test over every migration since production began: none drops, renames, changes a type, makes a column required, or adds a required column with no default; a statement marked `-- release-safe: <why>` is let through** (chosen) | Fails in `npm run check`, before a release; the marker makes taking something away a deliberate second step, written down | Pattern matching on SQL: a statement written unusually could slip past (a self-test checks each pattern catches its example) |
| Run the migrations in a separate release before the code                                                                                                                                                                             | The schema and code never meet out of order                                                                               | Two releases every time, for a risk that only some migrations carry                                                          |
| A rehearsal on a copy of production before each release (the restore drill, then the migrations)                                                                                                                                     | Tests the real data too                                                                                                   | Minutes and pence each release; the drill hasn't run once yet; it finds a broken migration but not a break of the old code   |

**Confidence:** high for the cases it names.

**Strongest case against:** it checks the shape of the SQL, not what the old code actually uses. A new `CHECK` constraint the old code's writes break, or a function replaced with different behaviour, gets through. Those are rarer, and the release's own check (the new build must report in before traffic moves) catches a new build that can't run. It doesn't catch an old build that breaks.

## What changes for Phil

Nothing to do. After a release, the worker's log says "Agents queued for a re-check against this build" about two minutes in, and each agent whose prompt changed logs "Agent re-synced". The domain move no longer needs the `save-demo-profile` task (RUNBOOK section 16).
